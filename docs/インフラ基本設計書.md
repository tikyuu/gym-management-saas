# インフラ基本設計書

## 文書の目的

本書は、パーソナルジム向け会員・予約管理SaaSのPhase 1をAWS上で安全かつ継続的に運用するため、インフラ構成と設計判断を定義する。

要件定義書に基づき、環境構成、ネットワーク、コンピュート、データベース、認証、監視、CI/CD、セキュリティおよび費用管理の基本方針を示し、AWS CDKによる詳細設計・構築・テスト・運用の判断基準として使用する。

## 設計方針

### アプリケーションの分割方針

Phase 1のバックエンドは、認証・認可、事業者・店舗、スタッフ・会員、メニュー・契約および予約のコードを機能ごとに分割し、1つのFastAPIアプリケーションとして実行するモジュラーモノリス構成とする。

バックエンドでは、1つのECRリポジトリで1種類のコンテナイメージを管理し、1つのECSサービスから同じアプリケーションを実行する複数のECSタスクを起動できる構成とする。データベースは1つのPostgreSQLを使用する。

予約と利用回数を同じデータベーストランザクションで処理しやすくし、ECS、監視およびCI/CDの運用対象を必要以上に増やさないことを採用理由とする。

機能間の依存をコード内部で明確に分離し、個別のデプロイ、負荷分散、障害分離または開発組織の分離が必要になった機能だけを、将来マイクロサービスとして分離できる構成とする。

### マネージドサービスの採用方針

Phase 1では、可用性、セキュリティおよび運用負荷を考慮し、AWSマネージドサービスを優先して採用する。

ただし、AWSサービスの追加自体を目的とせず、要件を満たすこと、費用に見合うこと、運用負荷を軽減できること、および構成を過度に複雑化しないことを確認したうえで採用を判断する。

### 環境分離方針

開発環境と本番環境は、誤操作、権限および障害の影響範囲を分離するため、AWSアカウントを分けて構築する。

AWS CDKのコードは環境間で可能な限り共通化し、リソース容量、可用性、削除保護、ログ保持期間および監視設定など、環境によって異なる値を設定として分離する。

ポートフォリオでの検証時は、実務を想定した分離構成を設計しつつ、不要なリソースを停止または削除して費用を抑える。

### リージョン・AZ方針

主な利用者を日本国内と想定し、通信遅延、データの保管場所およびAWSサービスの提供状況を考慮して、東京リージョン（`ap-northeast-1`）を使用する。

Phase 1では単一リージョン構成とし、東京リージョン内の独立した2つのAZを使用する。特定のAZ名は固定せず、各AWSアカウントで利用可能なAZからAWS CDKにより選択する。

マルチリージョン構成はPhase 1では採用せず、事業規模、復旧要件および費用を踏まえて将来検討する。

## 全体アーキテクチャ

Phase 1は、フロントエンド、認証、APIおよびデータベースを分離した構成とする。

```text
                         ┌──────────────┐
                         │   Cognito    │
                         │ ログイン・JWT発行 │
                         └──────▲───────┘
                                │
                  予約・管理操作で未ログインの場合
                                │
┌──────────────┐                │
│   ブラウザ    │────────────────┘
│ Reactを実行   │
└───────┬──────┘
        │
        │ 画面取得・API通信
        ▼
┌──────────────────┐
│ CloudFront + WAF │
└────────┬─────────┘
         │
         ├────────────────────→ S3
         │                      Reactを配信
         │
         └────────────────────→ ALB
                                  │
                                  │ APIを振り分ける
                                  ▼
                             ECS Fargate
                               FastAPI
                                  │
                                  │ データの読み書き
                                  ▼
                             PostgreSQL
```

CognitoはAPI通信の経路上へ直列に配置するのではなく、利用者を認証してJWTを発行する。FastAPIは、ブラウザから送信されたJWTを検証したうえで、認可された処理だけを実行する。

FastAPIのコンテナイメージはECRに保存し、機密情報はSecrets Managerで管理する。ログ、メトリクスおよびアラームはCloudWatchへ集約し、GitHub ActionsとAWS CDKを使用してテストおよびデプロイを自動化する。

## AWSアカウント構成

AWS Organizationsを使用し、管理、開発および本番の3つのAWSアカウントで構成する。

```text
AWS Organizations
├─ 管理アカウント
├─ 開発アカウント
└─ 本番アカウント
```

管理アカウントは、AWS Organizations、アカウント管理および請求の集約に使用し、アプリケーションを構成するVPC、ECS、データベースなどのリソースは配置しない。

開発アカウントにはdev環境、本番アカウントにはprod環境を構築し、誤操作、権限および障害の影響範囲をアカウント境界で分離する。

各アカウントのrootユーザーは初期設定および緊急時に限って使用し、通常の操作には使用しない。セキュリティ専用アカウントおよびログ保存専用アカウントは、Phase 1では設けず将来の拡張対象とする。

### AWSアカウントへのアクセス方針

人によるAWSアカウントへのアクセスはIAM Identity Centerへ統一し、通常作業用のIAMユーザーは作成しない。

利用者をグループへ所属させ、グループに対してAWSアカウントとPermission Setを割り当てる。開発アカウントでは構築・検証に必要な変更を許可し、本番アカウントでは通常時の権限を必要最小限に制限する。

GitHub ActionsによるAWS操作には、人の権限とは分離した環境別のIAMロールを使用する。具体的なPermission SetおよびIAMロールの権限は、IAM設計で定義する。

## DNS・ドメイン設計

DNSはRoute 53で管理し、所有する1つのルートドメインから、開発環境と本番環境のサブドメインを分ける。実際に使用するルートドメイン名は、ドメイン取得時に確定する。

```text
本番環境
├─ app.example.com
└─ auth.example.com

開発環境
├─ app.dev.example.com
└─ auth.dev.example.com
```

`app`はCloudFrontへ接続するWebアプリケーション用ドメイン、`auth`はCognitoのマネージドログインに使用する認証用ドメインとする。APIはCloudFrontを共通の入口とするため、Phase 1では独立したAPI用ドメインを設けない。

開発環境でも独自ドメインを使用し、本番環境と同等のHTTPS、Cognitoコールバックおよび認証遷移を事前に検証できる構成とする。

## ネットワーク設計

### VPC構成

開発アカウントと本番アカウントに、それぞれ環境専用のVPCを1つ構築する。

```text
開発アカウント
└─ dev用VPC

本番アカウント
└─ prod用VPC
```

AWSアカウントとVPCの両方で環境を分離し、誤操作、設定変更および障害の影響が別環境へ及ばない構成とする。Phase 1では、通信経路、費用および運用を必要以上に複雑化しないため、1環境内に複数のVPCを設けない。

### VPC CIDR

開発環境と本番環境には、重複しないプライベートIPアドレス範囲を割り当てる。

```text
開発VPC：10.10.0.0/16
本番VPC：10.20.0.0/16
```

将来のサブネット追加、ECSタスクの増加およびEKSなどへの拡張に備えて、各VPCには`/16`の範囲を確保する。環境間のCIDR重複を避け、将来VPC間接続が必要になった場合にも経路を識別できる構成とする。

### サブネット構成

各VPCは、外部公開、アプリケーション実行およびデータ保存の役割を分離するため、Public、Application、Databaseの3種類のサブネットで構成する。それぞれを2つのAZへ配置し、1環境あたり合計6つのサブネットを使用する。

```text
VPC
├─ AZ 1
│  ├─ Public Subnet
│  ├─ Application Subnet
│  └─ Database Subnet
└─ AZ 2
   ├─ Public Subnet
   ├─ Application Subnet
   └─ Database Subnet
```

- Public Subnetには、CloudFrontから通信を受けるALBを配置する。開発環境では、Application Subnetからの外向き通信を中継するZonal NAT Gatewayも配置する。
- Application SubnetにはECS Fargateのタスクを配置し、インターネットからの直接接続を許可しない。
- Database SubnetにはPostgreSQLデータベースを配置し、インターネットへの直接経路を設けず、ECSから必要な通信だけを許可する。

### Internet Gateway・ルートテーブル構成

各VPCにInternet Gatewayを1つ接続し、Public SubnetのデフォルトルートをInternet Gatewayへ向ける。

すべてのサブネットには、同じVPC内の通信に使用する`local`ルートが自動で作成される。サブネット同士を個別にルートへ登録せず、VPC CIDR宛ての`local`ルートを通じて通信する。

Application Subnetのデフォルトルートは、開発環境ではZonal NAT Gateway、本番環境ではRegional NAT Gatewayへ向ける。S3への通信にはS3 Gateway Endpointの経路を使用する。

Database Subnetにはインターネット向けのデフォルトルートを設定せず、VPC内部の通信だけを許可する。

```text
Public Subnet
├─ VPC CIDR   → local
└─ 0.0.0.0/0  → Internet Gateway

Application Subnet
├─ VPC CIDR   → local
├─ dev        ：0.0.0.0/0 → Zonal NAT Gateway
├─ prod       ：0.0.0.0/0 → Regional NAT Gateway
└─ S3宛て     → S3 Gateway Endpoint

Database Subnet
└─ VPC CIDR   → local
```

本番環境では、2つのAZにある同じ役割のサブネットでルートテーブルを共有する。Public Subnet用、Application Subnet用、Database Subnet用の3つに、AWSが自動作成するRegional NAT Gateway専用ルートテーブルを加え、合計4つとする。

Regional NAT Gateway専用ルートテーブルには、Internet Gatewayへの経路が自動設定される。

### NAT Gateway構成

開発環境は費用を抑えるため、Public Subnetのうち1つにZonal NAT Gatewayを1台配置し、2つのApplication Subnetで共有する。NAT Gatewayを配置したAZの障害時は外向き通信を継続できないため、この構成差を開発環境では許容する。

本番環境は、Automatic modeのRegional NAT Gatewayを1つ作成し、Application SubnetにECSタスクが存在する2つのAZへ自動展開する。Regional NAT Gatewayは特定のPublic Subnetへ配置せず、論理的に1つのNAT Gateway IDを使用しながら、AZごとの外向き通信経路と可用性を確保する。

### VPC Endpoint構成

開発環境と本番環境の両方にS3 Gateway Endpointを作成し、ECRのコンテナイメージレイヤー取得など、S3への通信がNAT Gatewayを経由しない構成とする。

ECR API、ECR Docker、CloudWatch LogsおよびSecrets ManagerのInterface Endpointは、Phase 1では作成しない。これらのAWSサービスおよびCognitoの公開エンドポイントへの通信は、Application SubnetからNAT Gatewayを経由する。

閉域接続に関する要件、NAT Gatewayを経由する通信量、可用性への影響およびInterface Endpointの固定費を継続的に確認し、費用またはセキュリティ上の効果が見込める場合に追加する。

### Security Group構成

ALBのSecurity Groupは、CloudFrontから送信されるHTTPS通信だけを受信できるようにする。

```text
ALB Security Group
└─ Inbound：CloudFrontのマネージドプレフィックスリスト → TCP 443
```

送信元にはAWS管理の`com.amazonaws.global.cloudfront.origin-facing`を使用し、CloudFrontのIPアドレスを個別に管理しない。`0.0.0.0/0`からの受信は許可せず、ALBへの直接アクセスをネットワークレベルで制限する。

ALBからECS Fargate上のFastAPIコンテナへの通信には、TCPポート`8000`を使用する。ECSのSecurity GroupはALBのSecurity Groupからの通信だけを許可し、インターネットやCloudFrontからECSへの直接接続を許可しない。

```text
ALB Security Group
└─ Outbound：ECS Security Group → TCP 8000

ECS Security Group
└─ Inbound：ALB Security Group → TCP 8000
```

PostgreSQLデータベースのSecurity Groupは、ECS Security Groupから送信されるPostgreSQL通信だけを受信できるようにする。

```text
ECS Security Group
└─ Outbound：Database Security Group → TCP 5432

Database Security Group
└─ Inbound：ECS Security Group → TCP 5432
```

インターネット、CloudFrontおよびALBからデータベースへの直接通信は許可しない。Security Groupはステートフルであるため、許可された接続に対するデータベースからECSへの応答通信について、逆方向の受信ルールは追加しない。

ECS Security Groupから外部サービスへの送信は、HTTPS通信に使用するTCP 443だけを許可する。送信先は`0.0.0.0/0`とするが、Application SubnetのルートテーブルによってNAT GatewayまたはS3 Gateway Endpointを経由させる。

```text
ECS Security GroupのOutbound
├─ Database Security Group → TCP 5432
└─ 0.0.0.0/0              → TCP 443
```

このHTTPS通信は、ECRからのコンテナイメージ取得、CloudWatch Logsへのログ送信、Secrets Managerからの秘密情報取得、CognitoのJWT検証情報取得およびS3への通信に使用する。すべてのプロトコルおよびポートを許可するデフォルトのOutboundルールは使用しない。

### Network ACL構成

Phase 1では、すべてのサブネットでデフォルトNetwork ACLを使用し、受信および送信通信を許可する。リソース間の通信制御はSecurity Groupを主な手段とする。

Network ACLはステートレスであり、独自設定では応答通信の一時ポートも管理する必要がある。現時点では、特定CIDRの明示的な拒否、組織の統制基準またはサブネット単位の追加防御要件がないため、設定ミスによる通信障害を避けることを優先する。
