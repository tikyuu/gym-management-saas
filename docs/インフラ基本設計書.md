# インフラ基本設計書

## 文書の目的

本書は、パーソナルジム向け会員・予約管理SaaSのPhase 1をAWS上で安全かつ継続的に運用するため、インフラ構成と設計判断を定義する。

要件定義書に基づき、環境構成、ネットワーク、コンピュート、データベース、認証、監視、CI/CD、セキュリティおよび費用管理の基本方針を示し、AWS CDKによる詳細設計・構築・テスト・運用の判断基準として使用する。

## 設計方針

### アプリケーションの分割方針

Phase 1のバックエンドは、認証・認可、事業者・店舗、スタッフ・会員、メニュー・契約および予約のコードを機能ごとに分割し、1つのFastAPIアプリケーションとして実行するモジュラーモノリス構成とする。

バックエンドでは、1つのECRリポジトリで1種類のコンテナイメージを管理し、1つのECSサービスから同じアプリケーションを実行する複数のECSタスクを起動できる構成とする。データベースは1つのPostgreSQLを使用する。

予約と利用回数を同じデータベーストランザクションで処理しやすくし、ECS、監視およびCI/CDの運用対象を必要以上に増やさないことを採用理由とする。

機能間の依存をコード内部で明確に分離し、個別のデプロイ、負荷分散、障害分離または開発組織の分離が必要になった機能だけを、将来マイクロサービスとして分離できる構成とする。

### マネージドサービスの採用方針

Phase 1では、可用性、セキュリティおよび運用負荷を考慮し、AWSマネージドサービスを優先して採用する。

ただし、AWSサービスの追加自体を目的とせず、要件を満たすこと、費用に見合うこと、運用負荷を軽減できること、および構成を過度に複雑化しないことを確認したうえで採用を判断する。

### 環境分離方針

開発環境と本番環境は、誤操作、権限および障害の影響範囲を分離するため、AWSアカウントを分けて構築する。

AWS CDKのコードは環境間で可能な限り共通化し、リソース容量、可用性、削除保護、ログ保持期間および監視設定など、環境によって異なる値を設定として分離する。

ポートフォリオでの検証時は、実務を想定した分離構成を設計しつつ、不要なリソースを停止または削除して費用を抑える。

### リージョン・AZ方針

主な利用者を日本国内と想定し、通信遅延、データの保管場所およびAWSサービスの提供状況を考慮して、東京リージョン（`ap-northeast-1`）を使用する。

Phase 1では単一リージョン構成とし、東京リージョン内の独立した2つのAZを使用する。CloudFront VPC Originの非対応AZである`apne1-az3`を除外し、利用可能なAZから2つを選択する。マルチアカウント間で同じ物理AZを識別できるよう、AZ名ではなくAZ IDを基準に判定する。

マルチリージョン構成はPhase 1では採用せず、事業規模、復旧要件および費用を踏まえて将来検討する。

## 全体アーキテクチャ

Phase 1は、フロントエンド、認証、APIおよびデータベースを分離した構成とする。

```text
                         ┌──────────────┐
                         │   Cognito    │
                         │ ログイン・JWT発行 │
                         └──────▲───────┘
                                │
                  予約・管理操作で未ログインの場合
                                │
┌──────────────┐                │
│   ブラウザ    │────────────────┘
│ Reactを実行   │
└───────┬──────┘
        │
        │ 画面取得・API通信
        ▼
┌──────────────────┐
│ CloudFront + WAF │
└────────┬─────────┘
         │
         ├────────────────────→ S3
         │                      Reactを配信
         │
         └────────────────────→ CloudFront VPC Origin
                                          │
                                          ▼
                                    Internal ALB
                                          │
                                          │ APIを振り分ける
                                          ▼
                                     ECS Fargate
                                       FastAPI
                                          │
                                          │ データの読み書き
                                          ▼
                                     PostgreSQL
```

CognitoはAPI通信の経路上へ直列に配置するのではなく、利用者を認証してJWTを発行する。FastAPIは、ブラウザから送信されたJWTを検証したうえで、認可された処理だけを実行する。

FastAPIのコンテナイメージはECRに保存し、機密情報はSecrets Managerで管理する。ログ、メトリクスおよびアラームはCloudWatchへ集約し、GitHub ActionsとAWS CDKを使用してテストおよびデプロイを自動化する。

## AWSアカウント構成

AWS Organizationsを使用し、管理、開発および本番の3つのAWSアカウントで構成する。

```text
AWS Organizations
├─ 管理アカウント
├─ 開発アカウント
└─ 本番アカウント
```

管理アカウントは、AWS Organizations、アカウント管理および請求の集約に使用し、アプリケーションを構成するVPC、ECS、データベースなどのリソースは配置しない。

開発アカウントにはdev環境、本番アカウントにはprod環境を構築し、誤操作、権限および障害の影響範囲をアカウント境界で分離する。

各アカウントのrootユーザーは初期設定および緊急時に限って使用し、通常の操作には使用しない。セキュリティ専用アカウントおよびログ保存専用アカウントは、Phase 1では設けず将来の拡張対象とする。

### AWSアカウントへのアクセス方針

人によるAWSアカウントへのアクセスはIAM Identity Centerへ統一し、通常作業用のIAMユーザーは作成しない。

利用者をグループへ所属させ、グループに対してAWSアカウントとPermission Setを割り当てる。開発アカウントでは構築・検証に必要な変更を許可し、本番アカウントでは通常時の権限を必要最小限に制限する。

GitHub ActionsによるAWS操作には、人の権限とは分離した環境別のIAMロールを使用する。具体的なPermission SetおよびIAMロールの権限は、IAM設計で定義する。

## DNS・ドメイン設計

DNSはRoute 53で管理し、所有する1つのルートドメインから、開発環境と本番環境のサブドメインを分ける。実際に使用するルートドメイン名は、ドメイン取得時に確定する。

```text
本番環境
├─ app.example.com
└─ auth.example.com

開発環境
├─ app.dev.example.com
└─ auth.dev.example.com
```

`app`はCloudFrontへ接続するWebアプリケーション用ドメイン、`auth`はCognitoのマネージドログインに使用する認証用ドメインとする。APIはCloudFrontを共通の入口とするため、Phase 1では独立したAPI用ドメインを設けない。

開発環境でも独自ドメインを使用し、本番環境と同等のHTTPS、Cognitoコールバックおよび認証遷移を事前に検証できる構成とする。

## ネットワーク設計

### VPC構成

開発アカウントと本番アカウントに、それぞれ環境専用のVPCを1つ構築する。

```text
開発アカウント
└─ dev用VPC

本番アカウント
└─ prod用VPC
```

AWSアカウントとVPCの両方で環境を分離し、誤操作、設定変更および障害の影響が別環境へ及ばない構成とする。Phase 1では、通信経路、費用および運用を必要以上に複雑化しないため、1環境内に複数のVPCを設けない。

### VPC CIDR

開発環境と本番環境には、重複しないプライベートIPアドレス範囲を割り当てる。

```text
開発VPC：10.10.0.0/16
本番VPC：10.20.0.0/16
```

将来のサブネット追加、ECSタスクの増加およびEKSなどへの拡張に備えて、各VPCには`/16`の範囲を確保する。環境間のCIDR重複を避け、将来VPC間接続が必要になった場合にも経路を識別できる構成とする。

### サブネット構成

Internal ALB、アプリケーション実行およびデータ保存で必要な通信経路が異なるため、Private Ingress、Application、Databaseの3種類のサブネットを分離する。それぞれを2つのAZへ配置する。

開発環境では、Zonal NAT Gatewayを配置するPublic Subnetも2つのAZへ作成し、合計8つのサブネットを使用する。本番環境ではRegional NAT Gatewayを使用するためPublic Subnetを作成せず、合計6つのサブネットを使用する。

```text
開発VPC
├─ AZ 1
│  ├─ Public Subnet
│  ├─ Private Ingress Subnet
│  ├─ Application Subnet
│  └─ Database Subnet
└─ AZ 2
   ├─ Public Subnet
   ├─ Private Ingress Subnet
   ├─ Application Subnet
   └─ Database Subnet

本番VPC
├─ AZ 1
│  ├─ Private Ingress Subnet
│  ├─ Application Subnet
│  └─ Database Subnet
└─ AZ 2
   ├─ Private Ingress Subnet
   ├─ Application Subnet
   └─ Database Subnet
```

- Public Subnetは開発環境だけに作成し、Application Subnetからの外向き通信を中継するZonal NAT Gatewayを配置する。
- Private Ingress Subnetには、CloudFront VPC Originとして使用するInternal ALBを配置する。インターネット向けのデフォルトルートは設定しない。
- Application SubnetにはECS Fargateのタスクを配置し、インターネットからの直接接続を許可しない。
- Database SubnetにはPostgreSQLデータベースを配置し、インターネットへの直接経路を設けず、ECSから必要な通信だけを許可する。

Internal ALBとECS Taskは同じVPC内で通信できるが、Internal ALBは外向き通信を必要とせず、ECS TaskはNAT Gateway経由の外向き通信を必要とする。異なるルーティング要件を明確に分離するため、同じApplication Subnetへ混在させない。

### Internet Gateway・ルートテーブル構成

各VPCにInternet Gatewayを1つ接続する。Internet GatewayはCloudFront VPC Originを使用するための前提条件だが、CloudFrontからInternal ALBへの通信経路には使用しない。

開発環境のPublic Subnetだけが、デフォルトルートをInternet Gatewayへ向ける。本番環境にはPublic Subnetを作成しない。

すべてのサブネットには、同じVPC内の通信に使用する`local`ルートが自動で作成される。サブネット同士を個別にルートへ登録せず、VPC CIDR宛ての`local`ルートを通じて通信する。

Application Subnetのデフォルトルートは、開発環境ではZonal NAT Gateway、本番環境ではRegional NAT Gatewayへ向ける。S3への通信にはS3 Gateway Endpointの経路を使用する。

Database Subnetにはインターネット向けのデフォルトルートを設定せず、VPC内部の通信だけを許可する。

```text
Public Subnet（開発環境のみ）
├─ VPC CIDR   → local
└─ 0.0.0.0/0  → Internet Gateway

Private Ingress Subnet
└─ VPC CIDR   → local

Application Subnet
├─ VPC CIDR   → local
├─ dev        ：0.0.0.0/0 → Zonal NAT Gateway
├─ prod       ：0.0.0.0/0 → Regional NAT Gateway
└─ S3宛て     → S3 Gateway Endpoint

Database Subnet
└─ VPC CIDR   → local
```

本番環境では、2つのAZにある同じ役割のサブネットでルートテーブルを共有する。Private Ingress Subnet用、Application Subnet用、Database Subnet用の3つに、AWSが自動作成するRegional NAT Gateway専用ルートテーブルを加え、合計4つとする。

Regional NAT Gateway専用ルートテーブルには、Internet Gatewayへの経路が自動設定される。

### NAT Gateway構成

開発環境は費用を抑えるため、Public Subnetのうち1つにZonal NAT Gatewayを1台配置し、2つのApplication Subnetで共有する。NAT Gatewayを配置したAZの障害時は外向き通信を継続できないため、この構成差を開発環境では許容する。

本番環境は、Automatic modeのRegional NAT Gatewayを1つ作成し、Application SubnetにECSタスクが存在する2つのAZへ自動展開する。Regional NAT Gatewayは特定のPublic Subnetへ配置せず、論理的に1つのNAT Gateway IDを使用しながら、AZごとの外向き通信経路と可用性を確保する。

### VPC Endpoint構成

開発環境と本番環境の両方にS3 Gateway Endpointを作成し、ECRのコンテナイメージレイヤー取得など、S3への通信がNAT Gatewayを経由しない構成とする。

ECR API、ECR Docker、CloudWatch LogsおよびSecrets ManagerのInterface Endpointは、Phase 1では作成しない。これらのAWSサービスおよびCognitoの公開エンドポイントへの通信は、Application SubnetからNAT Gatewayを経由する。

閉域接続に関する要件、NAT Gatewayを経由する通信量、可用性への影響およびInterface Endpointの固定費を継続的に確認し、費用またはセキュリティ上の効果が見込める場合に追加する。

### Security Group構成

Internal ALBのSecurity Groupは、CloudFront VPC Originから送信されるHTTPS通信だけを受信できるようにする。

```text
ALB Security Group
└─ Inbound：CloudFront-VPCOrigins-Service-SG → TCP 443
```

CloudFront VPC Originの作成時にAWSが自動作成するサービス管理Security Groupを送信元として許可する。AWS管理の`com.amazonaws.global.cloudfront.origin-facing`プレフィックスリストを恒常的な許可元には使用せず、対象のCloudFront VPC Originからの通信だけに制限する。Internal ALBにはインターネットから直接接続できない。

ALBからECS Fargate上のFastAPIコンテナへの通信には、TCPポート`8000`を使用する。ECSのSecurity GroupはALBのSecurity Groupからの通信だけを許可し、インターネットやCloudFrontからECSへの直接接続を許可しない。

```text
ALB Security Group
└─ Outbound：ECS Security Group → TCP 8000

ECS Security Group
└─ Inbound：ALB Security Group → TCP 8000
```

PostgreSQLデータベースのSecurity Groupは、ECS Security Groupから送信されるPostgreSQL通信だけを受信できるようにする。

```text
ECS Security Group
└─ Outbound：Database Security Group → TCP 5432

Database Security Group
└─ Inbound：ECS Security Group → TCP 5432
```

インターネット、CloudFrontおよびALBからデータベースへの直接通信は許可しない。Security Groupはステートフルであるため、許可された接続に対するデータベースからECSへの応答通信について、逆方向の受信ルールは追加しない。

ECS Security Groupから外部サービスへの送信は、HTTPS通信に使用するTCP 443だけを許可する。送信先は`0.0.0.0/0`とするが、Application SubnetのルートテーブルによってNAT GatewayまたはS3 Gateway Endpointを経由させる。

```text
ECS Security GroupのOutbound
├─ Database Security Group → TCP 5432
└─ 0.0.0.0/0              → TCP 443
```

このHTTPS通信は、ECRからのコンテナイメージ取得、CloudWatch Logsへのログ送信、Secrets Managerからの秘密情報取得、CognitoのJWT検証情報取得およびS3への通信に使用する。すべてのプロトコルおよびポートを許可するデフォルトのOutboundルールは使用しない。

### Network ACL構成

Phase 1では、すべてのサブネットでデフォルトNetwork ACLを使用し、受信および送信通信を許可する。リソース間の通信制御はSecurity Groupを主な手段とする。

Network ACLはステートレスであり、独自設定では応答通信の一時ポートも管理する必要がある。現時点では、特定CIDRの明示的な拒否、組織の統制基準またはサブネット単位の追加防御要件がないため、設定ミスによる通信障害を避けることを優先する。

## コンピュート設計（ECS Fargate）

### ECS構成

開発環境と本番環境に、それぞれ環境専用のECS Clusterを1つ作成する。各Clusterには、FastAPIを実行するECS Serviceを1つ配置する。

```text
ECS Cluster
└─ ECS Service
   └─ ECS Task
      └─ FastAPI Container
```

Phase 1では、1つのTask DefinitionにFastAPIコンテナを1つ定義する。同じTask Definitionから複数のTaskを起動し、ECS Serviceが必要なTask数を維持する。

### 実行基盤

コンテナの実行基盤にはAWS Fargateを使用する。EC2インスタンス、OS、ECS AgentおよびClusterのサーバー容量はAWSに管理を委ね、アプリケーション、コンテナイメージ、Task Definition、Task数、IAMおよびネットワーク設定を管理対象とする。

### Task数とAZ分散

開発環境は費用を抑えるため、Taskを1つ常時起動し、自動スケーリングを行わない。本番環境は可用性を確保するため、最低2つのTaskを2つのApplication Subnetへ分散して起動し、Availability Zone Rebalancingを有効にする。

```text
開発環境：1 Task
本番環境：最小2 Tasks、最大4 Tasks
```

### Service Auto Scaling

本番環境では、ECS Service全体の平均CPU使用率を目標値とするTarget Tracking Scalingを使用する。目標CPU使用率は`60%`とし、Task数を2から4の範囲で自動調整する。

メモリ使用率、ALBの1 Target当たりリクエスト数、API応答時間、5xxエラーおよびHealthy Task数は監視対象とするが、Phase 1では自動スケーリングの判断指標に使用しない。負荷試験でTask追加による改善効果を確認したうえで、必要な指標の追加を判断する。

### Task CPU・メモリ

FastAPI Taskの初期CPU・メモリは、次のとおりとする。

```text
開発環境：0.25 vCPU、0.5 GBメモリ
本番環境：0.5 vCPU、1 GBメモリ
```

本番環境は、画像や動画のようなCPU・メモリ負荷の高い処理をTask内で行わないこと、最低2つのTaskへ処理を分散することから、`0.5 vCPU`および`1 GB`を初期値とする。

この値は固定的な性能保証値ではない。`50 RPS`の負荷を30分間与え、CPU使用率、メモリ使用率、APIのP95応答時間、5xxエラー率およびTask数の変化を確認して妥当性を判断する。

容量変更が必要な場合は、CDKでCPU・メモリを変更して新しいTask Definition Revisionを作成し、ECS ServiceのローリングデプロイによってTaskを置き換える。Service Auto ScalingではCPU・メモリ容量を変更せず、Task数だけを自動調整する。

### コンテナポート

FastAPIコンテナはTCPポート`8000`で待ち受ける。ALBのTarget Groupは、ECS TaskのIPアドレスとポート`8000`へHTTP通信を転送する。

```text
CloudFront → VPC Origin → Internal ALB：HTTPS 443
ALB → ECS Task：HTTP 8000
```

Uvicornの待受ポート、Task Definitionのコンテナポート、Target Groupの転送ポートおよびSecurity Groupの許可ポートを`8000`で統一する。

### ヘルスチェック

ALBは、各ECS Taskの`GET /health`を定期的に実行し、ALBからTaskへの到達性とFastAPIの応答可否を確認する。異常と判定したTaskへのリクエスト転送を停止し、ECS ServiceによるTask交換につなげる。

```text
パス：/health
プロトコル：HTTP
ポート：8000
成功コード：200
実行間隔：30秒
タイムアウト：5秒
異常判定：2回連続失敗
正常復帰：2回連続成功
```

`/health`は認証を要求せず、FastAPIプロセスがHTTPリクエストへ応答できる場合に、機密情報を含まない`200 OK`を返す。PostgreSQLや外部APIへの接続確認は行わず、共有依存先の障害によってすべてのTaskが交換され続ける状態を防ぐ。

Task起動直後の準備時間を考慮し、ECS ServiceのHealth Check Grace Periodを`60秒`とする。PostgreSQLを含む主要機能の正常性は、外形監視、RDSメトリクス、APIの5xxおよび応答時間によって別途確認する。

### デプロイ方式

ECS Serviceのデプロイ方式にはローリングデプロイを使用する。正常な旧Taskを稼働させたまま新しいTaskを起動し、ALBヘルスチェックに成功したTaskから順次入れ替える。

```text
minimumHealthyPercent：100%
maximumPercent：200%
```

通常時に2つのTaskが稼働している場合、デプロイ中も最低2つのhealthyなTaskを維持し、旧Taskと新Taskを合わせて一時的に最大4つまで起動できるようにする。`maximumPercent`はデプロイ中のTask数を制御する設定であり、Service Auto Scalingの`maximumCapacity`とは区別する。

Deployment Circuit Breakerと自動ロールバックを有効にする。新しいTaskが起動またはALBヘルスチェックに繰り返し失敗した場合はデプロイを中止し、最後に正常稼働したTask Definition Revisionへ戻す。

Blue/Green、CanaryおよびLinearデプロイはPhase 1では採用しない。本番環境での事前検証、段階的なトラフィック移行または即時切り戻しに関する要件が高まった場合に再検討する。

### コンテナイメージ

FastAPIのDockerイメージはECRに保存し、イメージタグにはビルド対象のGit Commit SHAを使用する。`latest`はデプロイに使用しない。

```text
Git Commit SHA
↓
ECR Image Tag
↓
Task Definition Revisionのコンテナイメージ
↓
ECS Task
```

ECR Repositoryではイメージタグの上書きを禁止し、同じGit Commit SHAが異なるイメージを指さないようにする。これにより、稼働中のTaskとソースコードの対応を追跡でき、障害時には以前のイメージを指定したTask Definition Revisionへロールバックできるようにする。

## データベース設計（RDS for PostgreSQL）

### 採用方針

Phase 1はRDS for PostgreSQLを採用する。予約・契約の整合性をトランザクションや制約で管理し、バックアップと待機系への切り替えをマネージドサービスで実現する。

Auroraは初期構成では採用しない。初期費用と運用構成を抑え、負荷試験と運用実績をもとに必要な性能・可用性を確認する。将来の移行は可能だが、データ移行、互換性検証および接続先の切り替えが必要となるため、単なる設定変更として扱わない。

RDS Multi-AZ DBインスタンスのフェイルオーバーは通常60〜120秒であり、RTO 1時間の要件内で復旧できると判断する。Phase 1ではAuroraによる短いフェイルオーバー時間よりも、初期費用と構成の単純性を優先する。実際のRTO達成可否は、ECSからの再接続を含むフェイルオーバーテストで確認する。

### 環境別構成

| 項目 | 開発環境 | 本番環境 |
| --- | --- | --- |
| エンジン | PostgreSQL 18系 | PostgreSQL 18系 |
| 配置 | Single-AZ | Multi-AZ DBインスタンス |
| インスタンスクラス | `db.t4g.micro`を初期候補とする | 負荷試験と費用見積もりで確定する |
| ストレージ | gp3、初期20 GiB | gp3、初期20 GiB |
| ストレージ自動拡張の上限 | 50 GiB | 100 GiB |
| 自動バックアップ保持期間 | 1日 | 14日 |
| マイナーバージョン自動更新 | 有効 | 有効 |
| 削除保護 | 無効 | 有効 |
| CDKの削除方針 | `RemovalPolicy.DESTROY` | `RemovalPolicy.RETAIN` |

実装時に東京リージョンでのエンジンバージョン、インスタンスクラス、必要な拡張機能およびCDKの対応を確認し、マイナーバージョンを指定する。

本番は稼働系1台と別AZの同期待機系1台で構成する。待機系を読み取り負荷の分散には使用しない。3台構成のMulti-AZ DBクラスターとは区別する。公開前の一時的な検証ではSingle-AZを使用できるが、本番利用開始までにMulti-AZへ変更し、切り替えとアプリケーションの再接続を検証する。

RDSはDatabase Subnetへ配置し、パブリックアクセスを無効にする。接続元とポートはネットワーク設計で定義したSecurity Groupに従う。

### 容量管理

ストレージ自動拡張の上限は、最初から確保する容量ではない。空き容量の減少に応じて拡張するが、自動縮小は行われない。上限到達や急激な増加に備えて、空き容量、増加傾向および費用を監視する。

CPU・メモリの増強はインスタンスクラス変更で行う。ストレージ自動拡張ではCPU・メモリは増えない。クラス変更時の接続断や停止時間を事前に検証し、必要なメンテナンスを計画する。

### バックアップと復元

自動バックアップとPITRを有効にする。日次のバックアップとトランザクションログにより、保持期間内の復元可能な時点へ戻せるようにする。保持期間はバックアップを取得する間隔ではない。

| 環境 | バックアップ開始時間帯（日本時間） | RDS設定値（UTC） |
| --- | --- | --- |
| 開発 | 毎日04:00〜04:30 | `19:00-19:30` |
| 本番 | 毎日03:00〜03:30 | `18:00-18:30` |

上記は開始時間帯であり、30分以内の完了を保証するものではない。

PITRでは元のDBを巻き戻すのではなく、新しいDBを作成する。復元データの確認、アプリケーション接続先の切り替えおよび動作確認までを復旧手順に含める。匿名化・削除済み情報がバックアップから復活する場合の再処理も、要件定義書に従って行う。

RTO 1時間・RPO 5分は検証する目標とする。ログ転送の間隔だけでRPO達成とは判断せず、実際の復元可能時刻と復旧所要時間を確認する。本番運用開始前、および構成や復旧手順の重要な変更後に復元テストを行う。

重要な変更前には手動スナップショットを取得する。自動バックアップとは別に保持期限と削除担当を定め、不要なスナップショットを無期限に残さない。

### メンテナンスとバージョン更新

| 環境 | メンテナンス開始時間帯（日本時間） | RDS設定値（UTC） |
| --- | --- | --- |
| 開発 | 土曜05:00〜06:00 | `fri:20:00-fri:21:00` |
| 本番 | 日曜04:00〜05:00 | `sat:19:00-sat:20:00` |

マイナーバージョン自動更新を両環境で有効にする。更新対象はRDSが自動更新対象として指定したバージョンであり、常に最新へ更新されるわけではない。メジャーバージョン更新は自動化せず、互換性と復旧手順を検証して計画的に実施する。

開発と本番の時間帯を分けても、開発での検証結果に応じて本番更新を自動承認する仕組みにはならない。通知と保留中の変更を確認し、更新前後の動作確認を行う。時間帯の終了までにメンテナンスが完了するとは限らない。

RDS管理のマスターパスワードとRDS Blue/Green Deploymentsには併用制限があるため、Blue/Greenを利用できる前提にはしない。手動更新時の方式は、その時点の対応状況、認証情報の管理方式および停止時間を確認して確定する。マイナーバージョン自動更新がBlue/Greenで行われるわけではない。

参考：[AWS公式：RDS Blue/Green Deploymentsの制限](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/blue-green-deployments-considerations.html)

### 暗号化と削除保護

保存時の暗号化を有効にし、AWS管理KMSキー`aws/rds`を使用する。Phase 1ではCustomer Managed KMS Keyを作成しない。

DB接続はTLSを必須とし、`rds.force_ssl`を有効にする。アプリケーションとマイグレーション処理は、RDSの信頼されたCA証明書を使用し、証明書と接続先ホスト名を検証する。ドライバーに応じた具体的な設定はバックエンド設計で定義する。

本番は削除保護と`RETAIN`を併用する。スタック削除後もDBと費用が残るため、廃止時はバックアップと保持期限を確認したうえで、明示的に削除保護を解除して削除する。

### DBユーザーと認証情報

DBユーザーはPostgreSQL内の接続・操作権限を持つユーザーであり、IAMユーザーやサービスの会員とは区別する。

- 管理用：RDSにマスターパスワードの生成・Secrets Managerでの管理を任せ、通常のFastAPIには渡さない。
- アプリケーション用：管理用とは別に作成し、必要なテーブルの読み書きに限定する。パスワードはSecrets Managerで生成・保管する。
- 初期化・マイグレーション用：必要なDB権限と認証情報を持つ一時的なECS Taskで実行し、通常のアプリケーションTaskと分離する。

Secrets Managerにパスワードを作成するだけでは、PostgreSQL内のユーザーは作成されない。初期化処理でユーザーの作成と権限付与を行う。再実行時の扱いと、将来追加するテーブルへの権限付与はバックエンド設計で定義する。

DBホスト名・ポート・DB名は、CDKからECS Task Definitionの環境変数へ設定する。アプリケーション用の認証情報はSecret参照として設定し、ソースコードや平文のTask Definitionへ記載しない。

Secretの変更は稼働中コンテナの環境変数へ自動反映されない。パスワード変更と新しいTaskの起動を整合させる手順を、シークレット管理設計で定義する。

### 接続管理

Phase 1ではRDS Proxyを使用せず、FastAPI側のDB接続プールを利用する。接続を再利用し、DBが処理できる範囲に同時接続数を抑える。RDS Proxyは接続管理を補助するものであり、SQL処理そのものの高速化を保証するものではない。

接続数は1つのプールだけで判断せず、ECS Task数、各Taskのアプリケーションプロセス数、プロセスごとの最大接続数を合わせて見積もる。プールの一時追加接続、ローリングデプロイ中の新旧Taskの同時稼働、および運用・マイグレーション用の接続余裕も含める。

DBの接続上限とメモリ使用量を確認し、50 RPS・30分間の負荷試験で接続待ちやエラー、応答時間を検証する。プールサイズの「5」は説明用の例であり、確定値ではない。具体的な接続数、待機時間および再接続処理はバックエンド設計と負荷試験で確定する。

## IAM設計

### ECS Task用IAMロール

ECS Taskには、コンテナの起動準備に使用するTask Execution Roleと、起動後のFastAPIがAWSサービスを操作するために使用するTask Roleを設定する。2つのロールは用途が異なるため分離し、一方の権限を他方へ付与しない。

```text
Task Definition
├─ Task Execution Role：ECSによるTaskの起動準備
└─ Task Role          ：FastAPIによるAWSサービス操作
```

両方のロールは、信頼するサービスプリンシパルを`ecs-tasks.amazonaws.com`とする。開発環境と本番環境でロールを分離し、各環境のTaskが他環境のAWSリソースを操作できないようにする。

### Task Execution Role

Task Execution Roleには、AWS管理ポリシー`AmazonECSTaskExecutionRolePolicy`を付与し、ECRからのコンテナイメージ取得とCloudWatch Logsへのログ転送を許可する。

通常のアプリケーションTaskには、対象環境のアプリケーション用DB Secretに限定した`secretsmanager:GetSecretValue`を追加する。管理用DB Secretや、アカウント内のすべてのSecretを対象とする権限は付与しない。初期化・マイグレーション用Taskの認証情報取得権限は別途分離する。

Secrets Managerのデフォルト暗号化キーを使用するため、Phase 1では`kms:Decrypt`を追加しない。将来Customer Managed KMS Keyへ変更する場合は、対象キーに限定して復号権限を追加する。

### Task Role

Task Roleには、FastAPIが実行するAWS API操作だけを許可する。管理者によるスタッフ招待、利用停止、利用再開およびアカウント無効化など、Cognitoの管理操作に必要な権限を、対象環境のUser Poolに限定して付与する。

具体的なCognito IAM Actionは、認証設計とAPI設計で各処理をブラウザ、FastAPIまたはCognitoのどこで実行するか確定した後に定義する。使用しない管理操作を予測で許可しない。

店舗画像はPhase 1の対象外であるため、FastAPIのTask RoleにはS3オブジェクト操作権限を付与しない。将来画像機能を追加する場合は、対象バケットとオブジェクトキープレフィックスに限定した権限を追加する。

トレース送信に必要な権限は、監視設計でX-RayまたはOpenTelemetryの送信方式を決定した後にTask Roleへ追加する。
