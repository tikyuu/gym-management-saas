# インフラ基本設計書

## 文書の目的

本書は、パーソナルジム向け会員・予約管理SaaSのPhase 1をAWS上で安全かつ継続的に運用するため、インフラ構成と設計判断を定義する。

要件定義書に基づき、環境構成、ネットワーク、コンピュート、データベース、認証、監視、CI/CD、セキュリティおよび費用管理の基本方針を示し、AWS CDKによる詳細設計・構築・テスト・運用の判断基準として使用する。

## 設計方針

### アプリケーションの分割方針

Phase 1のバックエンドは、認証・認可、事業者・店舗、スタッフ・会員、メニュー・契約および予約のコードを機能ごとに分割し、1つのFastAPIアプリケーションとして実行するモジュラーモノリス構成とする。

バックエンドでは、1つのECRリポジトリで1種類のコンテナイメージを管理し、1つのECSサービスから同じアプリケーションを実行する複数のECSタスクを起動できる構成とする。データベースは1つのPostgreSQLを使用する。

予約と利用回数を同じデータベーストランザクションで処理しやすくし、ECS、監視およびCI/CDの運用対象を必要以上に増やさないことを採用理由とする。

機能間の依存をコード内部で明確に分離し、個別のデプロイ、負荷分散、障害分離または開発組織の分離が必要になった機能だけを、将来マイクロサービスとして分離できる構成とする。

### マネージドサービスの採用方針

Phase 1では、可用性、セキュリティおよび運用負荷を考慮し、AWSマネージドサービスを優先して採用する。

ただし、AWSサービスの追加自体を目的とせず、要件を満たすこと、費用に見合うこと、運用負荷を軽減できること、および構成を過度に複雑化しないことを確認したうえで採用を判断する。

### 環境分離方針

開発環境と本番環境は、誤操作、権限および障害の影響範囲を分離するため、AWSアカウントを分けて構築する。

AWS CDKのコードは環境間で可能な限り共通化し、リソース容量、可用性、削除保護、ログ保持期間および監視設定など、環境によって異なる値を設定として分離する。

ポートフォリオでの検証時は、実務を想定した分離構成を設計しつつ、不要なリソースを停止または削除して費用を抑える。

### リージョン・AZ方針

主な利用者を日本国内と想定し、通信遅延、データの保管場所およびAWSサービスの提供状況を考慮して、東京リージョン（`ap-northeast-1`）を使用する。

Phase 1では単一リージョン構成とし、東京リージョン内の独立した2つのAZを使用する。特定のAZ名は固定せず、各AWSアカウントで利用可能なAZからAWS CDKにより選択する。

マルチリージョン構成はPhase 1では採用せず、事業規模、復旧要件および費用を踏まえて将来検討する。

## 全体アーキテクチャ

Phase 1は、フロントエンド、認証、APIおよびデータベースを分離した構成とする。

```text
                         ┌──────────────┐
                         │   Cognito    │
                         │ ログイン・JWT発行 │
                         └──────▲───────┘
                                │
                  予約・管理操作で未ログインの場合
                                │
┌──────────────┐                │
│   ブラウザ    │────────────────┘
│ Reactを実行   │
└───────┬──────┘
        │
        │ 画面取得・API通信
        ▼
┌──────────────────┐
│ CloudFront + WAF │
└────────┬─────────┘
         │
         ├────────────────────→ S3
         │                      Reactを配信
         │
         └────────────────────→ ALB
                                  │
                                  │ APIを振り分ける
                                  ▼
                             ECS Fargate
                               FastAPI
                                  │
                                  │ データの読み書き
                                  ▼
                             PostgreSQL
```

CognitoはAPI通信の経路上へ直列に配置するのではなく、利用者を認証してJWTを発行する。FastAPIは、ブラウザから送信されたJWTを検証したうえで、認可された処理だけを実行する。

FastAPIのコンテナイメージはECRに保存し、機密情報はSecrets Managerで管理する。ログ、メトリクスおよびアラームはCloudWatchへ集約し、GitHub ActionsとAWS CDKを使用してテストおよびデプロイを自動化する。

## AWSアカウント構成

AWS Organizationsを使用し、管理、開発および本番の3つのAWSアカウントで構成する。

```text
AWS Organizations
├─ 管理アカウント
├─ 開発アカウント
└─ 本番アカウント
```

管理アカウントは、AWS Organizations、アカウント管理および請求の集約に使用し、アプリケーションを構成するVPC、ECS、データベースなどのリソースは配置しない。

開発アカウントにはdev環境、本番アカウントにはprod環境を構築し、誤操作、権限および障害の影響範囲をアカウント境界で分離する。

各アカウントのrootユーザーは初期設定および緊急時に限って使用し、通常の操作には使用しない。セキュリティ専用アカウントおよびログ保存専用アカウントは、Phase 1では設けず将来の拡張対象とする。
