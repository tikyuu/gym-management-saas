# 監視・ログ設計書

## 文書の目的

本書は、パーソナルジム向け会員・予約管理SaaSのPhase 1における監視、ログ、アラーム、通知およびトレースの設計を定義する。

利用者への影響を早期に検知し、障害が発生した場合に原因と影響範囲を調査できる状態を作ることを目的とする。また、要件定義書で定めたSLI、SLO、RTOおよびRPOを継続的に確認できるようにする。

監視項目を増やすこと自体を目的とせず、対応が必要な異常を検知できること、通知を受けた人が次に確認する情報を判断できること、および必要なログを適切な期間と費用で保持できることを重視する。

AWSサービスの全体構成と採用理由はインフラ基本設計書を正とし、本書では次の内容を具体化する。

- 監視対象と使用するメトリクス
- SLIの計測方法
- アラームの条件
- 通知先と通知方法
- 取得するログと記録項目
- ログの保存先、暗号化および保持期間
- Dashboardで確認する情報
- リクエストを追跡する方法
- 障害調査時の基本的な確認順序

## 監視設計

### CloudFront

| 監視項目 | メトリクス | 用途 | 統計・判定条件 |
| --- | --- | --- | --- |
| 5xxエラー率 | `5xxErrorRate` | アラート・Dashboard | Average、1分、5%以上が3回連続 |
| リクエスト数 | `Requests` | Dashboard | Sum、1分 |

#### 判断理由

CloudFrontからS3またはInternal ALBまでの公開経路で発生する利用者影響を早期に認知するため、`5xxErrorRate`を通知対象とする。原因は通知後にALB、ECS、FastAPIおよびRDSの監視情報から切り分ける。

可用性SLOの許容エラー率`0.1%`を大きく超える明確な障害の初期値として`5%`を採用する。一時的なエラーを除外しながら5分以内に認知するため、1分間隔で3回連続の超過を条件とし、負荷試験と運用実績に基づいて見直す。

欠損データは異常として扱わず、`Requests`はDashboardで母数を確認するために使用する。Phase 1では継続的な外形監視を導入せず、デプロイ後の公開経路の疎通確認とAWSサービスおよびアプリケーションの監視を組み合わせる。

CloudFrontはこの2つをPhase 1のDashboardへ表示する。ほかのメトリクスは、具体的な調査または運用判断に必要となった場合に追加する。CloudFrontはグローバルサービスであるため、メトリクスとアラームはバージニア北部リージョン（`us-east-1`）で管理する。

### WAF

| 監視項目 | メトリクス | 用途 | 統計・表示間隔 |
| --- | --- | --- | --- |
| 許可したリクエスト数 | `AllowedRequests` | Dashboard | Sum、1分 |
| 検知したリクエスト数 | `CountedRequests` | Dashboard | Sum、1分 |
| 遮断したリクエスト数 | `BlockedRequests` | Dashboard | Sum、1分 |

#### 判断理由

`AllowedRequests`、`CountedRequests`および`BlockedRequests`は同一のDashboardグラフへ表示し、WAFを通過、検知または遮断したリクエスト数の関係を確認する。Web ACL全体と個別ルールのメトリクスを使い分け、必要に応じてどのルールに一致したかを確認する。

開発環境ではルールアクションを`COUNT`とするため、`CountedRequests`により正常な画面操作やAPI通信の誤検知を確認する。本番環境ではルールアクションを`BLOCK`とするため、`BlockedRequests`により遮断数を確認する。

遮断数の増加だけでは、攻撃を正常に遮断した状態と正常な利用者を誤って遮断した状態を判別できない。通知過多を避けるため、Phase 1ではWAFメトリクスに単独のアラームを作成せず、詳細は後続で定義するWAFログを用いて調査する。

CloudFrontスコープのWeb ACLを対象とするため、WAFのメトリクスとDashboardはバージニア北部リージョン（`us-east-1`）で管理する。

### Cognito

| 監視項目 | メトリクス | 用途 | 統計・表示間隔 |
| --- | --- | --- | --- |
| ログイン成功率 | `SignInSuccesses` | Dashboard | Average、5分 |
| ログイン制限の発生数 | `SignInThrottles` | Dashboard | Sum、5分 |

#### 判断理由

`SignInSuccesses`は、ログイン試行に対する成功割合を確認するため、User PoolとApp Clientごとに5分間の平均値をDashboardへ表示する。会員用、スタッフ用およびSaaS運営者用の3つのUser Poolを別々の系列として表示し、どの認証系で変化が発生したかを判別する。

ログイン失敗にはパスワードの入力間違いなど利用者側の要因も含まれ、利用量が少ない段階では少数の失敗によって成功率が大きく変動する。そのため、Phase 1では`SignInSuccesses`を単独のアラーム判定に使用しない。

`SignInThrottles`は、Cognitoがログイン要求を制限した回数を確認するため、User PoolとApp Clientごとに5分間の合計値をDashboardへ表示する。Phase 1では通常値と利用量が確定していないため単独のアラームは作成せず、負荷試験と運用実績から継続時間および最低試行数を決定できる段階で通知条件を再検討する。

新規登録、トークン更新および外部IDプロバイダー連携のメトリクスは、障害調査または運用判断に必要となった場合に追加する。高度な脅威検知を提供するPlusプランは採用していないため、脅威保護のリスクメトリクスはPhase 1の監視対象に含めない。

Cognitoは東京リージョン（`ap-northeast-1`）へ作成するため、メトリクスとDashboardも東京リージョンで管理する。ログイン成功率とログイン制限数は単位が異なるため、同一グラフへ重ねず個別のグラフへ表示する。

### ALB

| 監視項目 | メトリクス | 用途 | 統計・判定条件 |
| --- | --- | --- | --- |
| 正常なECSタスク数 | `HealthyHostCount` | アラート・Dashboard | Maximum、1分、0が2回連続 |
| 異常なECSタスク数 | `UnHealthyHostCount` | Dashboard | Minimum、1分 |
| ALB自身の5xx | `HTTPCode_ELB_5XX_Count` | Dashboard | Sum、1分 |
| ECS・FastAPIの5xx | `HTTPCode_Target_5XX_Count` | Dashboard | Sum、1分 |
| API全体の応答時間 | `TargetResponseTime` | Dashboard | p95、1分 |
| APIリクエスト数 | `RequestCount` | Dashboard | Sum、1分 |

#### 判断理由

利用者影響はCloudFrontの`5xxErrorRate`で通知し、ALB自身が生成した5xxとECS・FastAPIが返した5xxは障害原因の切り分けに使用する。同じ障害による通知の重複を避けるため、Phase 1ではDashboard表示のみとし、運用上必要になった場合にアラートへの変更を検討する。

`TargetResponseTime`は、ALBからECS・FastAPIまでの応答時間の傾向を確認するため、p95を1分単位でDashboardへ表示する。すべてのAPIが集計対象となるため、予約作成および予約キャンセルのSLO判定には使用せず、対象操作ごとの応答時間はアプリケーション側のメトリクスで計測する。

`RequestCount`は、ALBへ届いたAPIリクエスト数を1分単位でDashboardへ表示する。CloudFrontの`Requests`が静的コンテンツとAPI通信を含むアクセス量を示すのに対し、ALBではAPI通信だけのアクセス量を確認し、エラーや応答時間の変化との関係を調査する。

`UnHealthyHostCount`は、正常な接続先が残っている状態でのタスク異常を確認するため、ALBとターゲットグループ単位でDashboardへ表示する。通知や異常判定には使用せず、数の推移を原因調査に利用する。

`UnHealthyHostCount`の欠損データは異常として扱わない。この条件では登録解除や全ターゲット不在を検知できない。

`HealthyHostCount`は、正常な処理先の喪失を検知するため、ALBとターゲットグループ全体を対象にCritical通知を行う。Maximumが0となる1分間の評価が2回連続した場合を条件とし、一時的な変動を抑えながら早期に通知する初期値として採用する。デプロイ時と障害時の実測で見直す。

本番環境では、`HealthyHostCount`の欠損データを異常として扱う。全ターゲット不在などで正常な接続先を確認できない状態を見逃さないためとする。開発環境では、計画停止による不要な通知を防ぐため、欠損データを正常として扱う。

### ECS

| 監視項目 | メトリクス | 用途 | 統計・判定条件 |
| --- | --- | --- | --- |
| メモリ使用率 | `MemoryUtilization` | アラート・Dashboard | Average、1分、85%以上が3回連続 |
| CPU使用率 | `CPUUtilization` | Dashboard | Average、1分 |

#### 判断理由

`MemoryUtilization`は、メモリ不足によるコンテナの強制終了を事前に検知するため、85%以上となる1分間の評価が3回連続した場合に通知する。本番環境の初期メモリ1GBに対して一定の余裕を残しながら、一時的な上昇を除外して5分以内に認知するための初期条件とし、負荷試験と運用実績に基づいて見直す。

`CPUUtilization`は、ECSサービスに割り当てたCPUに対する使用率を確認するため、1分単位の平均値をDashboardへ表示する。CPU使用率の上昇にはTarget Trackingによる自動スケーリングで対応するため、Phase 1ではCPU使用率だけを条件とするアラートは作成しない。

最大タスク数までスケールした状態でも高いCPU使用率が継続する場合は、自動スケーリングで解消できない処理能力不足として、タスク数とCPU使用率を組み合わせたアラートの追加を検討する。具体的な条件は負荷試験と運用実績に基づいて決定する。

Phase 1ではContainer Insightsを有効にせず、`RunningTaskCount`および`DesiredTaskCount`はCloudWatch Dashboardの監視項目に含めない。処理可能なタスク数はALBの`HealthyHostCount`で確認し、追加費用を抑える。タスクの再起動状況やタスク単位のCPU・メモリなど、ECS内部の詳細な調査が必要になった場合にContainer Insightsの採用を再検討する。

#### タスク異常停止イベント

ECSがEventBridgeへ送信するタスク状態変更イベントのうち、`TaskFailedToStart`および`EssentialContainerExited`を取得し、CloudWatch Logsへ保存する。タスクID、Task Definition Revision、停止日時、停止理由、停止コードおよびコンテナの終了コードを、起動失敗や実行中の異常終了を調査するために使用する。

単発のタスク異常停止はECS Serviceによる自動復旧の対象となるため、Phase 1では当該イベントから直接通知しない。正常な処理先が失われた場合は、ALBの`HealthyHostCount`アラートで通知する。

EventBridge Ruleと保存先のCloudWatch Log GroupはCDKで管理する。ログの保持期間はログ設計で定める。

#### デプロイ失敗イベント

Deployment Circuit Breakerが新しいTask Definition Revisionのデプロイ失敗を判定した場合に発行される`SERVICE_DEPLOYMENT_FAILED`を、EventBridgeで取得してCloudWatch Logsへ保存する。対象のECS Service、デプロイID、Task Definition Revision、発生日時および失敗理由を、ロールバックとデプロイ失敗の調査に使用する。

CI/CDパイプラインはECS Serviceのデプロイ完了を確認し、失敗または自動ロールバックが発生した場合はデプロイJobを失敗させる。当該イベントから直接通知は行わず、デプロイ担当者はCI/CDの実行結果で認知する。ロールバック後も正常な処理先が存在しない場合は、ALBの`HealthyHostCount`アラートで通知する。

### アプリケーションの可観測性

FastAPIのメトリクスとトレースは、OpenTelemetryを共通の計測方式として取得する。AWS向けの実装にはAWS Distro for OpenTelemetry（ADOT）を使用し、特定の監視サービスへアプリケーションコードを直接依存させない。

各ECS Taskでは、FastAPIコンテナとCloudWatch Agentコンテナを同じTask Definitionで起動する。FastAPIはOpenTelemetry Protocol（OTLP）を使用して同一Task内のCloudWatch Agentへテレメトリを送信し、CloudWatch Agentはサービスの稼働情報をCloudWatch Application Signalsへ、トレースをAWS X-Rayへ送信する。コンテナ間の通信には同一Task内の`localhost`を使用し、利用者のリクエスト経路にはCloudWatch Agentを配置しない。

```text
利用者
  ↓
ALB
  ↓
ECS Task
├─ FastAPI Container
│    └─ OpenTelemetryで計測
└─ CloudWatch Agent Container
     ├─ CloudWatch Application Signals
     └─ AWS X-Ray
```

HTTPメソッド、APIルート、ステータスコード、応答時間、外部通信およびデータベース呼び出しは、自動計装で取得できる範囲を利用する。予約作成や予約キャンセルの件数、業務上の拒否および処理結果など、業務上の意味を自動判定できない情報はFastAPIからカスタムメトリクスとして記録する。

Application SignalsはAPI全体のサービス状態と依存関係の把握に使用する。要件定義書でSLI対象とした予約作成および予約キャンセルは、対象外APIを混在させないため、アプリケーションのカスタムメトリクスから算出する。

#### 予約操作のSLIメトリクス

予約作成と予約キャンセルは、次の3つのカスタムメトリクスで計測する。

| 監視項目 | メトリクス | 種類 | 属性 | 記録するタイミング |
| --- | --- | --- | --- | --- |
| 有効な操作の試行数 | `reservation.operation.attempts` | Counter | `operation` | 認証、認可、入力および対象データの検証後、予約の業務処理を開始する直前 |
| 操作結果数 | `reservation.operation.results` | Counter | `operation`、`result` | 処理結果が確定した時点 |
| 正常に処理した操作の応答時間 | `reservation.operation.duration` | Histogram | `operation` | 正常な結果を返す時点 |

`operation`は`create`または`cancel`とする。`result`は、予約またはキャンセルが成立した`success`、業務ルールに基づく拒否を正しく返した`business_rejected`、システム障害により正しい結果を返せなかった`system_error`のいずれかとする。

入力不備、未認証、権限不足および存在しないデータの指定は、要件定義書に従って`attempts`へ含めない。重複予約、契約状態または利用可能回数などの業務ルールに基づく拒否は、正しい結果を返した操作として`business_rejected`へ記録する。

可用性SLIは、`success`と`business_rejected`の合計を`attempts`で除して算出する。処理開始後にTask停止やタイムアウトが発生して`results`を記録できなかった操作も、分母にだけ含まれることで正常に完了しなかった操作として扱う。

```text
可用性SLI
= (success + business_rejected) / attempts
```

`duration`は、FastAPIが有効な予約操作を受け付けてから、業務ルールとデータベース処理を終えてレスポンスを確定するまでを秒単位で記録する。`success`と`business_rejected`を対象とし、システム障害、入力不備、未認証、権限不足および存在しないデータの指定はレイテンシSLIから除外する。

CloudWatchでは`operation`によって予約作成と予約キャンセルを個別に集計し、両方を合わせた予約操作全体のSLIも確認できるようにする。

#### 予約操作のバーンレートアラーム

予約操作の可用性SLOは、ローリング28日間で`99.9%`とする。許容エラー率は`0.1%`であり、正常に完了しなかった操作数とバーンレートを次の式で算出する。

```text
正常に完了しなかった操作数
= attempts - (success + business_rejected)

実際のエラー率
= 正常に完了しなかった操作数 / attempts

バーンレート
= 実際のエラー率 / 0.1%
```

Phase 1では、予約作成と予約キャンセルを合わせた予約操作全体を対象に、次の条件をすべて満たした場合にCritical通知を行う。

| 判定項目 | 条件 |
| --- | --- |
| 最低操作数 | 直近1時間の`attempts`が20件以上 |
| 長期ウィンドウ | 直近1時間のバーンレートが`13.44`以上 |
| 短期ウィンドウ | 直近5分のバーンレートが`13.44`以上 |

バーンレート`13.44`は、28日間のエラーバジェットの`2%`を1時間で消費する速さとして算出した初期値である。1時間の長期ウィンドウで一時的な変動を除外し、5分の短期ウィンドウで現在もエラーが継続していることを確認する。

最低操作数はアラーム判定だけに使用し、20件未満の場合もSLIの計算から除外しない。低トラフィック時の単発エラーによる過剰な通知を抑えつつ、実際に正常処理できなかった事実はSLOへ反映する。最低操作数とバーンレートの閾値は、本番環境の利用量と障害実績に基づいて見直す。

予約作成と予約キャンセル別のSLI、エラー率およびバーンレートはDashboardへ表示し、予約操作全体のアラームが発生した場合の影響範囲確認に使用する。予約操作が最低件数に満たない時間帯は、ALB、ECSおよびRDSなどの基盤監視で補完する。ただし、無アクセス時の公開経路全体の障害を継続的に検知することはPhase 1の対象外とする。

テレメトリの属性には、パスワード、トークン、氏名、メールアドレス、電話番号などの機密情報・個人情報を含めない。会員ID、予約IDなど値の種類が増え続ける情報はカスタムメトリクスの属性に使用せず、必要な調査情報はログまたはトレースで扱う。

FastAPIのアプリケーションログは標準出力へ出力し、ECSの`awslogs`ログドライバーを通じてCloudWatch Logsへ保存する。OpenTelemetryはメトリクスとトレースの計測に使用し、Phase 1ではログ転送経路を置き換えない。

CloudWatch Agentの設定、サイドカー、必要なIAM権限、Application SignalsおよびX-Rayの有効化はCDKで管理する。Phase 1ではContainer Insightsを有効にせず、アプリケーションの可観測性とECS基盤の詳細監視を別の目的として扱う。

### RDS

| 監視項目 | メトリクス | 用途 | 統計・表示間隔 |
| --- | --- | --- | --- |
| CPU使用率 | `CPUUtilization` | アラート・Dashboard | Average、1分、90%以上が5回連続 |
| 空きストレージ容量 | `FreeStorageSpace` | Dashboard | Minimum、5分 |
| DB接続数 | `DatabaseConnections` | Dashboard | Average、1分 |
| 利用可能メモリ | `FreeableMemory` | Dashboard | Average、1分 |
| スワップ使用量 | `SwapUsage` | Dashboard | Average、1分 |
| 読み取り遅延 | `ReadLatency` | Dashboard | Average、1分 |
| 書き込み遅延 | `WriteLatency` | Dashboard | Average、1分 |

#### 判断理由

`FreeStorageSpace`は、RDSで現在利用できる空きストレージ容量と減少傾向を確認するため、5分間の最小値をDashboardへ表示する。

Phase 1ではストレージ自動拡張を有効にしており、空き容量の低下に応じてRDSが容量を拡張する。正常な自動拡張のたびに不要な通知が発生することを避けるため、`FreeStorageSpace`単独のアラームは作成しない。

容量不足によって予約操作を正常に処理できない場合は、アプリケーションの`system_error`と予約操作のバーンレートアラームで利用者影響を検知する。ストレージ使用量が自動拡張の上限へ近づく運用になった場合は、RDSイベントを使用した通知の追加を検討する。

`DatabaseConnections`は、通常時とアクセス増加時の接続数、および処理後も接続数が増え続ける接続リークの兆候を確認するため、1分間の平均値をDashboardへ表示する。

接続上限はRDSのインスタンスクラスとPostgreSQL設定によって異なり、FastAPIの接続プール数も詳細設計で決定するため、Phase 1の基本設計時点では単独のアラームを作成しない。本番構成と負荷試験結果の確定後、必要な場合は最大接続数に対する使用割合を基準にアラームを追加する。

`CPUUtilization`は、SQL処理の増加によるRDSのCPU飽和を検知するため、1分間の平均値が90%以上となる状態が5回連続した場合にCritical通知を行う。一時的なCPU上昇による通知を抑えながら、RDSが自動的にコンピュート性能を拡張しないことを考慮した初期条件とする。

CPU使用率が80%台の状態はDashboardで傾向を確認する。負荷試験ではCPU使用率と予約操作のP95応答時間を比較し、90%へ到達する前に性能要件を満たせなくなる場合は、実測結果に基づいて閾値を引き下げる。

`FreeableMemory`はRDSが利用できるメモリ量、`SwapUsage`はメモリ不足を補うためにディスクを使用している量を確認するため、1分間の平均値をDashboardへ表示する。空きメモリの減少とスワップ使用量の増加を組み合わせ、メモリ圧迫の可能性を判断する。

メモリ容量と適切な閾値はRDSのインスタンスクラスに依存する。本番環境のインスタンスクラスは負荷試験と費用見積もりで確定するため、Phase 1の基本設計時点では固定値のアラームを作成しない。負荷試験で通常値と性能影響を確認した後、環境ごとに閾値を決定する。

`ReadLatency`と`WriteLatency`は、RDSがストレージの読み書き1回あたりに要した平均時間を確認するため、1分間の平均値をDashboardへ表示する。これらはAPI全体の応答時間ではなく、RDS内部のストレージI/Oの遅延を表す。

許容できる遅延はワークロードとアプリケーションの性能要件に依存するため、Phase 1では単独のアラームを作成しない。予約操作のP95応答時間が悪化した場合に、CPU使用率、メモリおよび読み書き遅延を比較し、RDSのストレージI/Oが原因かを調査する。

#### RDS重大障害イベント

本番環境のRDS DBインスタンスが発行する`failure`カテゴリのイベントをEventBridge Ruleで検知し、既存のSNS Topicを通じてCritical通知を行う。対象は`source` が`aws.rds`、`detail-type` が`RDS DB Instance Event`であり、対象RDSのARNとイベントカテゴリで絞り込む。

ストレージ自動拡張の失敗、KMSキーへのアクセス失敗、DBインスタンスの復旧困難な状態など、RDSが直接検出した重大障害を早期に認知することを目的とする。個別のRDSイベントIDは固定せず、`failure`カテゴリに該当するイベントをまとめて対象とする。

正常なバックアップ開始・完了通知による通知過多を避けるため、`backup`カテゴリは通知対象としない。開発環境では当該EventBridge Ruleを作成せず、本イベント専用のLambdaおよびCloudWatch Log Groupも追加しない。

RDSイベント通知は基盤障害の直接的な認知に使用し、CloudFront、ALBおよび予約操作SLIによる利用者影響の監視と組み合わせる。

## ログ設計

### 保存先と保持期間

| ログ | 保存先 | 開発環境 | 本番環境 |
| --- | --- | --- | --- |
| FastAPIコンテナログ | CloudWatch Logs | 60日 | 60日 |
| Cognitoのメール・SMS配送エラーログ | CloudWatch Logs | 60日 | 60日 |
| RDS PostgreSQLログ | CloudWatch Logs | 60日 | 60日 |
| WAFログ | CloudWatch Logs | 60日 | 60日 |
| CloudFrontアクセスログ | S3 | 60日 | 60日 |
| ALBアクセスログ | S3 | 60日 | 60日 |
| CloudTrailログ | S3 | 365日 | 365日 |

障害調査時に検索する運用ログはCloudWatch Logs、リクエストごとに継続して発生するアクセスログはS3へ保存する。通常の運用ログとアクセスログは環境間の管理差を減らすため60日に統一し、AWSアカウントおよびリソースへの操作を追跡するCloudTrailログだけを365日保存する。

CloudWatch Logsの保持期間はLog Groupごとに設定する。S3へ保存するログはLifecycle Ruleによって保持期間経過後に自動削除し、手作業による削除を前提としない。

### FastAPIコンテナログ

FastAPIは、API処理の結果、エラー、処理時間およびリクエストIDなどのアプリケーションログをJSON形式で標準出力または標準エラーへ出力する。ECS Task Definitionで`awslogs`ログドライバーを設定し、コンテナの標準出力と標準エラーをCloudWatch Logsへ転送する。

FastAPIがログの内容を生成し、ECSがログをCloudWatch Logsへ転送するため、FastAPIログとECSログを別々のLog Groupへ重複保存しない。ECSタスクの起動失敗、停止およびデプロイ失敗は、コンテナログではなくECS Service EventおよびEventBridgeで確認する。

すべてのAPIリクエストログに、次の共通項目を記録する。

| 項目 | 内容 |
| --- | --- |
| `timestamp` | UTCで記録するログ発生日時 |
| `level` | `INFO`、`WARNING`または`ERROR` |
| `event` | 検索・集計に使用する固定のイベント名 |
| `message` | 人が処理内容を理解するためのメッセージ |
| `request_id` | 1回のAPI通信を追跡するID |
| `trace_id` | CloudWatch LogsとOpenTelemetryのトレースを関連付けるID |
| `method` | HTTPメソッド |
| `path` | APIのリクエストパス |
| `status_code` | APIが返したHTTPステータスコード |
| `duration_ms` | APIが応答するまでに要したミリ秒単位の時間 |

開発環境と本番環境はAWSアカウントおよびLog Groupで分離するため、`environment`は各ログへ重複して記録しない。日時はAWSサービス間のログを同じ時間軸で照合できるようUTCで統一し、利用者画面と管理画面では`Asia/Tokyo`へ変換して表示する。

利用者または予約を特定して調査する必要がある場合に限り、`user_id`や`reservation_id`などの内部IDをログへ記録する。想定外のサーバーエラーでは`error_type`と`stack_trace`を追加し、入力不備、未認証、権限不足および予約競合など想定内の4xxレスポンスにはスタックトレースを記録しない。

パスワード、JWT、リフレッシュトークン、Cookie、Authorizationヘッダー、Secrets Managerの値、DB接続情報、氏名、メールアドレス、電話番号および生年月日はログへ記録しない。例外情報とリクエスト内容を出力する場合も、機密情報および個人情報が含まれないように制御する。

内部IDのように値の種類が増え続ける情報はCloudWatch Metricsのディメンションへ使用せず、ログとトレースによる個別調査だけに使用する。

### Cognitoログ

Cognito Essentialsでは、ログイン成功率とスロットリング数をCloudWatch Metricsで確認し、メールアドレス確認やパスワード再設定などのメール・SMS配送エラーをCloudWatch Logsへ保存する。Cognitoの設定変更および管理API操作は、AWSアカウント全体のCloudTrailログで追跡する。

利用者ごとの詳細な認証行動とリスク評価を出力する脅威保護のユーザーアクティビティログはPlusプランの機能であるため、Phase 1では保存対象に含めない。

### アクセスログの機密情報保護

WAFログでは、`Authorization`ヘッダーと`Cookie`ヘッダーを`redactedFields`に指定し、認証情報を`REDACTED`として記録する。マスキングはWAFの検証処理には影響せず、ログへ保存する値だけを隠す。

WAFの`redactedFields`はサンプリングされたリクエストへ適用されないため、Phase 1ではWeb ACLと各ルールのリクエストサンプリングを無効化する。WAFが検知または遮断したリクエストの調査には、CloudWatch Logsへ保存したWAFログを使用する。

パスワード、JWT、リフレッシュトークン、メールアドレス、電話番号などの機密情報および個人情報は、URLのクエリパラメータへ含めない。検索条件、ページ番号など機密性のない値だけをクエリパラメータとして使用し、必要な個人情報はHTTPSで暗号化されたリクエストボディで送信する。

### ログの閲覧権限

開発者には開発環境のログ、本番運用者には業務上必要な本番環境のログだけを閲覧できる権限を、IAM Identity CenterのPermission Setで付与する。GitHub Actionsにはログの閲覧権限を付与しない。

ECS Task Execution Roleには、対象のCloudWatch Log Groupへログを転送するための書き込み権限だけを付与し、ログの検索・読み取り権限は付与しない。ログの書き込み主体と閲覧主体を分離し、環境と保存先を限定した最小権限とする。

### ログの暗号化

CloudWatch LogsはAWS標準の保存時暗号化を使用し、S3へ保存するアクセスログとCloudTrailログはS3管理キーによるサーバーサイド暗号化（SSE-S3）を使用する。Phase 1の要件はIAMとバケットポリシーによるアクセス制御で満たせるため、ログ専用のCustomer Managed KMS Keyは作成しない。

顧客管理鍵による復号権限の分離、鍵利用の監査または組織のセキュリティ基準への準拠が必要になった場合は、Customer Managed KMS Keyへの変更を検討する。

### CloudTrailログ

管理アカウントでOrganization Trailを作成し、管理、開発および本番アカウントの全リージョンを対象として、読み取りと書き込みのManagement Eventsを記録する。AWSリソースの作成、設定変更、削除および管理API操作を、実行者、実行日時、接続元および対象リソースと関連付けて追跡する。

Data Eventsは、画像保存用S3バケットとReact配信用S3バケットの`PutObject`および`DeleteObject`だけを記録する。CloudFrontによる`GetObject`などの読み取り操作、ログ保存用S3バケットおよびPhase 1で使用しないサービスのData Eventsは、ログ量と費用を抑えるため対象外とする。

CloudTrailログは管理アカウントの専用S3バケットへ集約する。S3 Block Public AccessとVersioningを有効化し、開発および本番アカウントからログを削除できないバケットポリシーを設定する。閲覧権限は管理アカウントの監査・運用権限へ限定する。

CloudTrailのLog File Validationを有効化し、ログファイルが配信後に変更または削除されていないことを検証できるようにする。Log File Validationは改ざんを防止する機能ではないため、S3のアクセス制御と組み合わせて使用する。S3 Object Lockは、保持期間中の削除不能による運用負荷を考慮し、Phase 1では採用しない。

### デプロイ後の疎通確認

本番環境へのデプロイ後に、CI/CDパイプラインからCloudFrontの公開URLを通じて`GET /api/health`を実行する。`200 OK`を取得できない場合はデプロイJobを失敗とし、CloudFront、VPC Origin、Internal ALB、ECSおよびFastAPIまでの公開経路を確認する。

`GET /api/health`は認証を要求せず、PostgreSQLなどの依存先へは接続しない。この疎通確認はデプロイ直後の異常検知を目的とし、サービス稼働中の継続監視には使用しない。

Phase 1では、CloudWatch SyntheticsのCanary、実行用Lambda、アーティファクト保存用S3および専用ログを追加しない。無アクセス時を含む継続的な外形監視が必要になった場合に、本番環境の公開URLを対象とするCanaryの導入を再検討する。
